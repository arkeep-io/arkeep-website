title: Destinations
description: Where backups are stored. Every destination type, its fields, and how to create, edit, clone and delete destinations.

A destination is where backups are stored. Each one holds a single restic repository that every policy
writing to it shares. Retention and integrity checks are set on the destination: see
[Retention and integrity checks](/docs/guides/retention-and-checks/).

Create one with **Destinations → New Destination** (admin).

## Types

### Local Path

A directory on the agent's host.

| Field | Required | Notes |
|---|---|---|
| **Path** | yes | For example `/mnt/backups`. With a Docker agent, type the host path; see [Local destinations in Docker](/docs/installation/docker-compose/#local-destinations-in-docker). |

The path is resolved on the agent that runs the job, so a local destination only makes sense for policies
on that machine (or a path every agent can reach, such as an NFS mount). If the path is a mount point, a
backup that runs while the disk or share is not mounted fails; see
[When the repository is missing](#when-the-repository-is-missing).

### S3 / Object Storage

Any S3-compatible service: AWS S3, Backblaze B2, Cloudflare R2, MinIO, Wasabi, and more.

| Field | Required | Notes |
|---|---|---|
| **Bucket** | yes | |
| **Endpoint** | yes | The provider's S3 endpoint, for example `s3.amazonaws.com`, `s3.eu-central-003.backblazeb2.com`, `<account>.r2.cloudflarestorage.com`. Leaving it blank does not mean AWS. |
| **Region** | no | Sent as `AWS_DEFAULT_REGION` |
| **Prefix** | no | A folder inside the bucket, so several repositories can share one bucket |
| **Access Key ID** | yes | |
| **Secret Access Key** | yes | |

The repository is `s3:<endpoint>/<bucket>/<prefix>`.

### SFTP

Any SSH server.

| Field | Required | Notes |
|---|---|---|
| **Host** | yes | |
| **Port** | no | Defaults to 22 |
| **Username** | yes | |
| **Remote Path** | yes | |
| **Password** | one of the two | Password authentication |
| **Private Key (PEM)** | one of the two | Key authentication |
| **Host Key** | no, recommended | The server's public host key, see below |

SFTP connections go through the agent's bundled rclone, so the agent host needs no SSH client or
`~/.ssh` setup. The credentials you enter are used directly.

### Host key

Paste the server's host key, as printed by `ssh-keyscan` run from a network you trust:

```bash
ssh-keyscan -p 22 backup.example.com
```

Every line of the output is accepted, hashed hosts and bare `ssh-ed25519 AAAA…` keys included; comment
lines are ignored. Agents then refuse to connect to a server presenting another key, and the job fails
with *knownhosts: key mismatch*. If the server's key changes on purpose, paste the new one.

:::caution
Without a host key the server's identity is not verified: whoever sits on the network path between the
agent and the server could receive the SFTP credentials and the backup data (encrypted by restic).
:::

### REST Server

A self-hosted restic [rest-server](https://github.com/restic/rest-server).

| Field | Required | Notes |
|---|---|---|
| **REST Server URL** | yes | `http://` or `https://` |
| **Username**, **Password** | no | HTTP basic auth, if the server uses it |

rest-server's `--append-only` mode pairs well with an [append-only destination](/docs/guides/retention-and-checks/#append-only-destinations).

### Rclone

Any of rclone's 40+ backends: Google Drive, OneDrive, Azure Blob, Dropbox, and more.

| Field | Required | Notes |
|---|---|---|
| **Remote Name** | yes | Must match a remote configured in `rclone.conf` on the agent |
| **Path** | yes | Path inside the remote |

Rclone destinations take no credentials in Arkeep: configure the remote, with its credentials, in
`rclone.conf` on each agent that writes to it. The remote name accepts letters, digits, `_ . + @`,
spaces and dashes; it cannot be an rclone connection string.

## Credentials

Credentials are encrypted at rest and never shown again after saving. When you edit a destination, leave
the credential fields blank to keep the current ones.

## Common fields

- **Name** (required).
- **Enabled** (when you edit or duplicate a destination; new ones start enabled): a disabled destination is paused. Backups skip it and do not list it in the job, and the
  periodic snapshot sync, scheduled retention sweeps and scheduled integrity checks leave it alone.
  **Run Retention Now** and **Run Check Now** still work. A backup whose destinations are all disabled
  fails with *all destinations disabled: backup not run*.

## Import an existing repository

When creating a destination, turn on **Import existing repository** if the location already holds a
restic repository, for example from before you used Arkeep. Pick an **Agent** that can reach it and enter
its **Repository Password**. Arkeep tests the repository through that agent before saving anything, then
lists its snapshots. See [Importing and syncing snapshots](/docs/guides/importing-and-sync/).

## The Destinations list

Columns: **Name**, **Type**, **Status**, **Usage** (repository size, sortable) and **Created**. Badges next
to the name tell you more:

| Badge | Meaning |
|---|---|
| Existing repo | The destination was imported and stores its repository password |
| Append-only | Snapshots here are never deleted or pruned |
| No retention | Retention is off |
| Retention needs reconfiguration | After an upgrade, policies that used to have different retention share this destination; set its retention once |
| Integrity check failed | The last integrity check failed |

**Status** shows Enabled or Disabled and, while the repository is in use, **Busy** or **N backups running**,
linking to the job.

Admin actions: **Edit**, **Duplicate** (copies the settings without the credentials, named "Copy of …"),
**Import snapshots** and **Delete**.

## Destination details

The destination page shows **Used by N policies**, the repository size, the retention schedule, the last
integrity check and the recent jobs on it. Admins also get **Run Retention Now**, **Run Check Now**,
**Sync Snapshots**, **New Repository** (see below), **Edit** and **Delete**.

While a job holds the repository, the page explains which job and since when; other jobs on the
destination wait for it (see [Jobs](/docs/guides/jobs/#statuses)).

## When the repository is missing

The first backup to a destination creates its restic repository. From the moment anything succeeds on
it (a backup, a retention sweep, an integrity check, an import or a snapshot sync), Arkeep never creates
it again: if the repository is gone, backups to the destination fail with *repository not found* and send
the usual failure notification. This protects against writing into the wrong place, for example an
unmounted USB disk or NFS share, where a new empty repository would otherwise be created in the bare
mount point and the backups would go to the system disk instead.

When the repository is missing, check that the storage is mounted and reachable from the agent, then run
the backup again. If you replaced the storage on purpose and want to start over at the same location, use
**New Repository** on the destination page: the next backup creates a new, empty repository there, and
snapshots that are not in it leave the snapshot list. Nothing on the storage is deleted, and the action
is recorded in the audit log. Changing the destination's
location (path, bucket, prefix, URL or remote) has the same effect, since the new location holds a new
repository.

## Delete a destination

Deleting a destination erases its stored credentials and repository password and removes it from every
policy. Its snapshots stay listed, but browsing and downloading them is no longer possible, and restoring
one asks for the destination's credentials again. **The backup data on the storage is not touched.**
