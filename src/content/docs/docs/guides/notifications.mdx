Arkeep notifies you when jobs finish and when agents go offline or come back, by **email**, **webhook**,
**notification providers** (push and chat services such as Gotify, ntfy, Telegram or Discord) and **in-app**
notification. A [job report](#job-report) can also email a summary of all finished jobs every hour, day, week or month.

## Events

Turn events on or off in **Settings → Notifications**:

| Event | Default |
|---|---|
| Job failed | on |
| Job succeeded | on |
| Agent went offline | on |
| Agent came back online | off |

Job events cover every job type (backups, restores, retention sweeps and integrity checks), with titles such
as *Backup failed: web-server* (policy name) or *Retention completed: NAS* (destination name). Jobs that give up after repeated resumes
or time out in the queue are reported as failed jobs.

Each policy can override the two job events with **On success** and **On failure**: **Use global setting**,
**Always** or **Never**. See [Policies](/docs/guides/policies/#notifications).

These toggles and overrides decide what is sent by email, webhook and notification providers.

## Channels

Email, webhook and notification providers are independent: use any combination. In **Settings → Notifications**:

- **Send email notifications** (on by default) emails every enabled event. Turn it off to keep only the
  webhook: no email is attempted and no SMTP error is logged. Password reset emails are still sent.
- **Send webhook notifications** (off by default) posts every enabled event to your endpoint. See
  [Webhook](#webhook).
- **Notification providers** each receive every enabled event, and can be turned on and off one by one.
  See [Notification providers](#notification-providers).

A channel or provider turned off (or a provider deleted) also drops its deliveries still waiting for a retry, so turning it back on never sends
old notifications. In-app notifications are always created.

The [job report](#job-report) is not an event and has its own setting: it does not depend on these toggles
and channels.

## Email

Set up the mail server in **Settings → SMTP**:

| Field | Notes |
|---|---|
| **Host** | Required |
| **Port** | For example 587 |
| **Implicit TLS** | On for SMTPS on port 465; off for STARTTLS (587) or plaintext |
| **Authentication** | Turn on to enter **Username** and **Password**. Leave the password blank to keep the current one, unless you change the host: a new host needs the password again. |
| **From Address** | Required |
| **From Name** | `Arkeep` by default |
| **Notification Recipients** | Addresses to notify. When empty, every active admin is notified. With **Send email notifications** off, they receive no event emails, but still the [job report](#job-report) when it is on. |

**Send test email** sends a message with the values in the form, saved or not, to your own address (the
admin who clicks it), and shows the server's answer or the exact error. With the password left blank it
uses the saved one, but only for the saved host: to test another server, type its password.

The same SMTP server sends [password reset](/docs/guides/users-and-2fa/#forgotten-password) emails.

## Job report

The job report is one email that lists every job that finished since the previous report. Use it instead of
one email per job, for example with **Job succeeded** turned off, or next to the event emails as a daily
overview.

Set it in **Settings → Notifications → Job report**:

| Frequency | When it is sent |
|---|---|
| **Off** | Never (default) |
| **Hourly** | Every hour at the set **Minute** (0 to 59), e.g. `30` for 08:30, 09:30… |
| **Daily** | Every day at the set **Time** (`07:00` by default), in the server's time zone, shown next to the field |
| **Weekly** | Every week on the set **Day** (Monday by default) at the set **Time** |
| **Monthly** | Every month on the set **Day of the month** (1 to 28, so it exists in every month; the 1st by default) at the set **Time** |

The email shows the number of jobs, succeeded and failed (cancelled and interrupted only when there are
any), and one table per job type: backups, retention sweeps, integrity checks and restores. Each row has the
job (policy or destination name) with its agent, start time, duration and status; the backup table also shows
the data added to the repositories. A long report is shortened, with the number of jobs left out under each
table: the full list is on the **Jobs** page.

- **Period:** each report covers the jobs that ended since the previous one, so no job is listed twice or
  left out, even after a change of frequency. A job still running is in the next report. The first report
  after turning it on covers the jobs from that moment.
- **No jobs, no email:** when no job finished in the period, nothing is sent.
- **Every job:** the report lists all jobs, whatever the [event toggles](#events) and the policy overrides
  say, and it is sent even when **Send email notifications** is off. To get only the report, turn off the job
  events or the email channel.
- **Delivery:** to the **Notification Recipients**, or to every active admin when none are set, through the
  [SMTP server](#email). While SMTP is not configured nothing is sent, and the next report sent covers the
  jobs since the last one that went out.
- **Server downtime:** a report that fell due while the server was down is sent when it starts again.

## Webhook

In **Settings → Notifications**, turn on **Send webhook notifications** and set:

- **Webhook URL**: any `http://` or `https://` endpoint. Every event is sent as a `POST` with a JSON body.
- **Webhook Secret**: optional; when set, every request is signed (see below). Leave it blank to keep the
  current one.

**Send test webhook** posts a `test` event to the URL in the form, saved or not, signed with the secret in
the form or, when it is blank, with the saved one. It works even with the webhook not saved yet, and shows
the HTTP status or the network error when the delivery fails.

The payload is described in [Webhook events](/docs/reference/webhook-events/).

### Signature verification

When a webhook secret is set, every request carries an `X-Arkeep-Signature` header with an HMAC-SHA256 of the
raw request body, the same convention GitHub and Stripe use:

```text
X-Arkeep-Signature: sha256=<lowercase hex>
```

Always verify the signature **before** processing the payload.

```go
// Go
func verifyArkeepSignature(body []byte, secret, header string) bool {
    expected := strings.TrimPrefix(header, "sha256=")
    mac := hmac.New(sha256.New, []byte(secret))
    mac.Write(body)
    actual := hex.EncodeToString(mac.Sum(nil))
    return hmac.Equal([]byte(expected), []byte(actual))
}
```

```python
# Python
import hmac, hashlib

def verify_arkeep_signature(body: bytes, secret: str, header: str) -> bool:
    expected = header.removeprefix("sha256=")
    actual = hmac.new(secret.encode(), body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, actual)
```

```js
// Node.js
const crypto = require('crypto')

function verifyArkeepSignature(body, secret, header) {
  const expected = header.replace(/^sha256=/, '')
  const actual = crypto.createHmac('sha256', secret).update(body).digest('hex')
  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(actual))
}
```

## Notification providers

Notification providers send events straight to a push or chat service, without a relay. In
**Settings → Notifications → Notification providers**, click **Add provider**, choose the service and fill
in what it needs: Arkeep builds the rest. Add as many providers as you like, for example Gotify on your phone
and a Telegram group for the team.

| Service | What you need |
|---|---|
| **Gotify** | Server URL and the token of an application created in Gotify |
| **ntfy** | Server URL (`https://ntfy.sh` or your own), topic, and an access token if the server or topic requires one |
| **Pushover** | User key, application API token, and optionally the devices to notify |
| **Telegram** | Bot token (from [@BotFather](https://t.me/BotFather)) and chat IDs or `@channel` names; the bot must be in the chats |
| **Discord** | The channel's webhook URL (**Channel Settings → Integrations → Webhooks**) |
| **Matrix** | Homeserver URL, user, password and optionally the rooms (otherwise every room the user has joined) |
| **Slack** | The URL of an [incoming webhook](https://api.slack.com/messaging/webhooks) |
| **Microsoft Teams** | The URL of a Workflows (Power Automate) webhook, *Post to a channel when a webhook request is received* |
| **Google Chat** | The space's webhook URL (**Apps & integrations → Webhooks**) |
| **Mattermost** | The URL of an incoming webhook (**Integrations → Incoming Webhooks**) |
| **Other** | A [shoutrrr](https://github.com/nicholas-fedor/shoutrrr) URL, for any other service shoutrrr supports |

A server URL without a scheme means `https://`; an `http://` URL turns TLS off. For Gotify and ntfy behind a
reverse proxy, include the base path (`https://example.com/gotify`).

Tokens, passwords, topics and webhook URLs are encrypted at rest and never shown again: when you edit a
provider, leave them blank to keep the current values. For Gotify, ntfy and Matrix they are kept only while
the server in **URL** stays the same: pointing it at another host needs them again, so that saved secrets
are never sent to another server. To drop the optional ntfy access token, click
**Remove the saved access token**.

### Priority per event

Gotify, ntfy and Pushover take a priority, set per event on each provider. Leave it empty for the service
default.

| Service | Values | Example: silent success, loud failure |
|---|---|---|
| **Gotify** | `0` to `10`. `0` shows no notification on Android, `8` and above pop up with sound and vibration | success `0`, failure `8` |
| **ntfy** | `1` (min) to `5` (max), or `min`, `low`, `default`, `high`, `max` | success `min`, failure `max` |
| **Pushover** | `-2` (no alert) to `1` (high); `2` (emergency) repeats until acknowledged | success `-2`, failure `1` |

Arkeep checks the values when you save, so a typo is reported at once rather than at the next failed backup.
The **Other** type accepts a priority only for services that have one.

### Testing

**Send test notification** sends a test message with the values in the form, saved or not, with the priority
of **Job failed**, and shows the service's error when it fails. For a saved provider, blank secret fields use
the saved values, on the saved server only.

## Delivery and retries

Email, webhook and notification provider deliveries are retried up to three times: immediately, after 5 minutes and after 30 minutes.

A [job report](#job-report) that could not be sent is retried after 5 minutes. The daily report is retried
again after 30 more minutes; the weekly and monthly reports after 30 minutes, 2 hours and 6 hours more. If it
still fails, the next report covers its jobs.

## In-app notifications

The bell in the interface shows the latest 20 notifications to **administrators**, with an unread counter.
Users with the read-only `user` role receive no in-app notifications and do not see the bell.
Click one to mark it read, or **Mark all as read**. In-app notifications are always created, whatever the
event toggles say. Read notifications are deleted 30 days after they were read; unread ones are kept.

## Integrations

Slack, Discord, Telegram and the other services under [Notification providers](#notification-providers) are
simpler to set up as providers. The recipes below use the generic webhook, for integrations that need its
JSON payload.

### Slack

1. Create an [incoming webhook](https://api.slack.com/messaging/webhooks) in your workspace.
2. Paste its URL into **Webhook URL**.

Arkeep's `text` field is Slack's message body, so nothing else is needed.

### Discord

1. In your server, open **Channel Settings → Integrations → Webhooks** and create a webhook.
2. Paste its URL into **Webhook URL** and append `/slack`. Discord's own endpoint expects a `content`
   field and rejects Arkeep's payload as an empty message; the `/slack` endpoint accepts Slack-compatible
   payloads, whose `text` field Arkeep sends.

```text
https://discord.com/api/webhooks/<id>/<token>/slack
```

### n8n

1. Add a **Webhook** trigger node (method `POST`, respond immediately) and paste its URL into Arkeep.
2. Optionally add a **Code** node that verifies `X-Arkeep-Signature`.
3. Add a **Switch** node on `{{ $json.type }}`: `job_failure`, `job_success`, `agent_offline`, `agent_online`.
4. Connect Slack, PagerDuty, Telegram, email or anything else to each branch.

Fields are available as `{{ $json.payload.policy_name }}`, `{{ $json.payload.error }}` and so on.

### Zapier

1. Create a Zap with **Webhooks by Zapier → Catch Hook** and paste the hook URL into Arkeep.
2. Run a backup to send a sample event.
3. Use `type`, `title`, `text`, `payload__policy_name`, `payload__error` and `timestamp` in your actions, and a
   **Filter** step on `type` (for example only `job_failure`).

## A backup that never runs

Notifications fire when a job ends, so a backup that never starts (server down, scheduler stuck, policy
disabled by mistake) stays silent. [Healthchecks.io](/docs/guides/healthchecks/) covers that case.
